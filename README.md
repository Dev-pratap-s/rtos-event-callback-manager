# RTOS Event & Callback Manager

## Overview

This project implements a simple **RTOS-style Event & Callback Manager** in C.

The system simulates how an embedded payment soundbox can handle events using:

- Fixed-size FIFO event queue
- Event dispatcher
- Callback registration
- Function pointers
- Event processing
- CLI-based commands

### Architecture

```text
Event Producer
      |
      v
Fixed-Size FIFO Event Queue
      |
      v
Event Dispatcher
      |
      v
Registered Callback
      |
      v
Payment / Network / Audio Action
```

---

## Problem Statement

The goal is to simulate an RTOS-style event handling system for a payment soundbox.

Different events can be generated by the system, placed into a FIFO queue, and processed later by the registered callback.

The implementation must ensure:

- Events are processed in FIFO order.
- Queue size is fixed.
- No dynamic memory allocation is used for the queue.
- Each event is dispatched to its registered callback.
- An event is processed only once.
- Invalid commands and inputs are handled safely.
- Queue full and empty conditions are handled safely.

---

## Supported Events

| Event | Description |
|---|---|
| `PAYMENT_RECEIVED` | Payment received |
| `PAYMENT_SUCCESS` | Payment completed successfully |
| `PAYMENT_FAILED` | Payment failed |
| `NETWORK_CONNECTED` | Network connection established |
| `NETWORK_DISCONNECTED` | Network connection lost |
| `LOW_BATTERY` | Low battery warning |

---

## Supported Callbacks

| Callback | Purpose |
|---|---|
| `paymentReceivedCallback` | Handles received payment |
| `paymentSuccessCallback` | Handles successful payment |
| `paymentFailedCallback` | Handles failed payment |
| `networkCallback` | Handles network connected/disconnected events |
| `batteryCallback` | Handles low battery event |

## Callback Mapping

The following callback registrations are supported:

```text
PAYMENT_RECEIVED      -> paymentReceivedCallback
PAYMENT_SUCCESS       -> paymentSuccessCallback
PAYMENT_FAILED        -> paymentFailedCallback
NETWORK_CONNECTED     -> networkCallback
NETWORK_DISCONNECTED  -> networkCallback
LOW_BATTERY           -> batteryCallback
```

## Commands

### 1. REGISTER

Registers a callback for an event.

```text
REGISTER <event> <callback>
```

Example:

```text
REGISTER PAYMENT_RECEIVED paymentReceivedCallback
```

Output:

```text
Registered paymentReceivedCallback for PAYMENT_RECEIVED
```

---

### 2. PUSH

Adds an event to the FIFO queue.

Payment events require an amount.

```text
PUSH <event> [amount]
```

Examples:

```text
PUSH PAYMENT_RECEIVED 500
PUSH PAYMENT_SUCCESS 500
PUSH PAYMENT_FAILED 200
PUSH NETWORK_CONNECTED
PUSH NETWORK_DISCONNECTED
PUSH LOW_BATTERY
```

---

### 3. PROCESS

Processes one event from the front of the queue.

```text
PROCESS
```

Example:

```text
Processing PAYMENT_RECEIVED
Callback: Payment received: 500
```

Every `PROCESS` command handles only one event.

---

### 4. LIST

Displays all events currently present in the queue without removing them.

```text
LIST
```

Example:

```text
Events in queue:
1. PAYMENT_RECEIVED | Amount: 500
2. PAYMENT_SUCCESS | Amount: 500
3. NETWORK_CONNECTED
```

`LIST` is non-destructive.

---

### 5. STATUS

Displays the current queue status and registered callbacks.

```text
STATUS
```

Example:

```text
========== STATUS ==========
Queue size      : 10
Events in queue : 2
Free spaces     : 8

Registered callbacks:
PAYMENT_RECEIVED -> paymentReceivedCallback
PAYMENT_SUCCESS -> paymentSuccessCallback
============================
```

---

### 6. EXIT

Terminates the program.

```text
EXIT
```

## FIFO Event Queue

The event queue uses a fixed-size array.

```c
#define QUEUE_SIZE 10
```

The queue maintains:

- `front` - position of the next event to process
- `rear` - position where the next event will be inserted
- `count` - number of events currently stored

### Queue Operations

The implementation provides separate functions for:

```text
initQueue()
isQueueEmpty()
isQueueFull()
pushEvent()
popEvent()
```

The queue uses circular indexing:

```c
(rear + 1) % QUEUE_SIZE
```

and

```c
(front + 1) % QUEUE_SIZE
```

This allows the queue to reuse free spaces after events are processed.

---

## Event Structure

Each event contains at least:

```c
typedef struct
{
    EventType type;
    int amount;
} Event;
```

`amount` is used for payment-related events.

For network and battery events, the amount remains `0`.

---

## Function Pointer and Callback System

Callbacks are represented using a function pointer typedef:

```c
typedef void (*EventCallback)(Event event);
```

This allows different callback functions to be registered and invoked dynamically.

For example:

```text
PAYMENT_RECEIVED
        |
        v
paymentReceivedCallback()
```

and:

```text
LOW_BATTERY
        |
        v
batteryCallback()
```

The dispatcher finds the registered callback for the event and invokes it.

---

## Event Processing Flow

When an event is pushed:

```text
PUSH PAYMENT_RECEIVED 500
        |
        v
Event created
        |
        v
Event added to FIFO queue
```

When processing:

```text
PROCESS
   |
   v
Pop event from queue
   |
   v
Find registered callback
   |
   v
Invoke callback
   |
   v
Perform simulated action
```

## Error Handling

The program safely handles several invalid conditions.

### Invalid Event

```text
> REGISTER ABC paymentSuccessCallback
Error: invalid event type
```

### Invalid Callback

```text
> REGISTER PAYMENT_SUCCESS abc
Error: invalid callback
```

### Duplicate Registration

```text
> REGISTER PAYMENT_SUCCESS paymentSuccessCallback
Registered paymentSuccessCallback for PAYMENT_SUCCESS

> REGISTER PAYMENT_SUCCESS paymentSuccessCallback
Error: callback already registered for PAYMENT_SUCCESS
```

### Invalid Payment Amount

```text
> PUSH PAYMENT_SUCCESS -500
Error: amount must be greater than 0
```

### Empty Queue

```text
> PROCESS
No events in queue
```

### Unknown Command

```text
> HELLO
Error: unknown command
```

### Full Queue

If the queue contains 10 events:

```text
> PUSH LOW_BATTERY
Error: event queue is full
```

The program does not add the event when the queue is full.

## Design Approach

The project is divided into separate logical components.

### Event Management

Responsible for:

- Event types
- Event creation
- Event name parsing

### Queue Management

Responsible for:

- Queue initialization
- FIFO insertion
- FIFO removal
- Full/empty checking

### Callback Management

Responsible for:

- Callback registration
- Duplicate registration checking
- Callback lookup
- Callback invocation

### Command Interface

Responsible for:

- Reading user commands
- Validating input
- Executing requested operations

---

## Important Assumptions

1. Queue size is fixed at 10.
2. No dynamic memory allocation is used for the event queue.
3. One callback can be registered for each event type.
4. Network events share the same `networkCallback`.
5. Payment events require a positive amount.
6. `LIST` does not remove events from the queue.
7. `PROCESS` processes exactly one event.
8. If an event has no registered callback, the program reports an error instead of crashing.
9. The implementation uses standard C11 features.
